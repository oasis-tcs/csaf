### News from the Editors

- **New CSAF Python package (Stefan Hagen).** Stefan Hagen announced he has started work on a CSAF package (published under a different package name to avoid interfering with users) that provides validation and creation APIs for CSAF documents. He is looking for friendly users to try it against their own documents and house rules, on both the producer and consumer sides. Interested members should contact him by email; he will share the link to the package in the chat.
- **New publication system (Stefan Hagen).** Stefan Hagen described the new publication toolchain that replaces the previous LaTeX/TeX Live setup (~12 GB, fragile across systems). It uses **Typst** (an MIT-licensed tool), is roughly ten times faster, produces understandable intermediate source, and works on normal systems (e.g. installable via Homebrew). Together with Michael Colletta, he added **quality gates** so the TC does not vote to submit documents that then require many editor/admin iterations over minor issues (e.g. front-matter titles). The gate logic was extracted into a YAML configuration file kept in the repositories, making the system more configuration-driven. It has already been used in around five specifications (including CSAF) and produces a pass/fail protocol; combined with a manifest, it can verify that rendered resources match the source tree.
- **Editor revision (Thomas Schmidt).** Thomas Schmidt noted that, beyond the under-the-hood changes Stefan described, an editor revision is being prepared for the TC meeting. It contains mostly minor editorial changes—fixing test files and editorial clarifications—so no detailed walkthrough was necessary.

### GitHub Issues & Pull Requests

#### Issue [#965](https://github.com/oasis-tcs/csaf/issues/965) - Allow for other identifiers than CVE

- **Background:** Issue #965 was opened by Jacco (NCSC-NL) on 30 April 2025 following the MITRE CVE funding uncertainty, asking whether other vulnerability enumeration schemes (e.g. EUVD, CNVD, GHSA, GCVE) should be usable alongside CVE. The discussion established that `/vulnerabilities[]/ids[]` already accommodates any non-CVE identifier, and that guidance could be improved by registering `system_name` values and validation `pattern`s for the `text`. The work landed via the Registry for Vulnerability ID Systems (RVISC), and the issue had been closed as completed by Justin Murphy shortly before the meeting.
- Thomas Schmidt explained that CVE remains the first-class citizen while other vulnerability IDs are supported through `ids`, and that the establishment of RVISC resolves the request. Interested parties wanting a specific ID system registered should open separate issues.
- Sergii Demianchuk asked whether the issue needed to be closed given a corresponding registration path exists; Thomas Schmidt clarified this is a cleanup of completed work, with no further tracking work implied.
- A motion was presented by Thomas Schmidt to close Issue #965 as resolved through the establishment of the [RVISC registry](https://github.com/oasis-tcs/csaf/tree/master/registry/id), with interested parties opening separate issues to register their ID systems. The motion was seconded by Christoph Plutte. No objections, discussions or concerns were raised. The motion carries. (The resolution was recorded on the issue after the meeting.)

#### Issue [#1482](https://github.com/oasis-tcs/csaf/issues/1482) - Adoption of CSAF for vulnerability report submission pre-embargo

- **Background:** Issue #1482 (full title: "Adoption of CSAF for vulnerability reports submission pre-embargo using TLP markings and phased release to public CSAF report") was opened by Vijay Sarvepalli (SEI/CERT/CC) on 25 June, following discussions at FIRSTCON26 with Ericsson PSIRT (Christoph Plutte) about standardizing volumetric and AI-assisted vulnerability reports. It proposes using CSAF as the standard interface for vulnerability report submission during the pre-embargo phase (using TLP markings), and outlines a **CSAF Vulnerability Reporting Form (CSAF-VRF)** profile that maps existing CSAF 2.1 fields (e.g. `document.category = csaf_vrf`, `distribution`/TLP, `notes`, `product_status.under_investigation`, `involvements`) to the discoverer → coordinator → vendor workflow.
- Thomas Schmidt explained the issue interweaves three things: (1) a vulnerability reporting profile, (2) cleaning up involvements so they can be used in that profile to communicate pre-embargo events, and (3) additional fields for which CERT/CC suggested an extension. Because these are hard to work on together, he proposed splitting the work into three separate parts:
  1. Use Issue #1482 to build the CSAF vulnerability report profile.
  2. Create separate issues (on the fly, as needed) for fields suggested in the CERT/CC extension that are worth importing into CSAF core (e.g. a contact PGP key URL, which had no issue yet).
  3. Handle the rework of involvements separately via existing Issue #1486.
- Sergii Demianchuk confirmed the third part maps to existing Issue #1486 and asked whether corresponding issues exist for the first two; Thomas Schmidt confirmed #1482 will be used for the first and that the second is still under analysis.
- Justin Murphy supported the approach and offered to coordinate with Vijay Sarvepalli. Christoph Plutte (who had discussed this with Vijay at the FIRST conference and attended the VRDX / vulnerability-coordination special-interest-group sessions) also endorsed splitting the work up and offered to contribute.
- **Assignments:** Justin Murphy and Vijay Sarvepalli were assigned to the vulnerability report profile (#1482); Christoph Plutte and Justin Murphy to the involvements rework (#1486), coordinating offline with Vijay Sarvepalli (who could not join today).

#### Issue [#1486](https://github.com/oasis-tcs/csaf/issues/1486) - Rework `involvements`

- **Background:** Issue #1486 was opened by Thomas Schmidt on 3 July to rework the `involvements` object so it can reflect all actions and states that can occur in CVD and coordination, using [Vultron](https://certcc.github.io/Vultron/) (CERT/CC) as a starting point. Vijay Sarvepalli's draft PR [#1487](https://github.com/oasis-tcs/csaf/pull/1487) was an initial attempt.
- Thomas Schmidt described the approach: study the Vultron project and its states (which should cover what can occur in coordination), design the involvements from scratch, and then work on the mapping from the existing CSAF 2.0 structure. Vijay Sarvepalli's pending pull request (#1487) was rejected with comments.
- Justin Murphy asked about the example in Vijay's pull request that contained an extension. Thomas Schmidt clarified that the extension suggested in PR #1487 is out of scope for the involvements rework and, as it is not an official (TC-voted) extension, it should not make its way silently into the repository.
- Christoph Plutte asked about the intended scope of the rework. Thomas Schmidt explained the current model has a party and a status (with the end date from CSAF 2.0); CSAF 2.1 added a way to link an involvement to its counterpart (useful in multi-party coordination) and links to products and product groups so a researcher can express which products they were contacted about.
- A motion was presented by Thomas Schmidt to add a reworked involvement section to CSAF 2.1 as discussed and to task Christoph Plutte, Justin Murphy and Vijay Sarvepalli to provide a draft. The motion was seconded by Christoph Plutte, who asked for clarification of the scope. No objections, discussions or concerns were raised. The motion carries.

#### PR [#1487](https://github.com/oasis-tcs/csaf/pull/1487) - Involvements document level (contact email and OpenPGP key fields)

- **Background:** Draft PR #1487, by Vijay Sarvepalli, extracts the `involvements` array into a reusable `involvements_t` definition and references it from both the `document` and `vulnerabilities` sections (enabling document-level involvements), adding an example document. Reviewing the changed files, Thomas Schmidt focused on the `contact_pgp_url` field used in the example.
- Thomas Schmidt noted Vijay Sarvepalli's suggestion that a researcher can provide a URL to their PGP key, and argued it is also useful for a vendor to link the key used to sign material. Sergii Demianchuk asked about the benefit of a core field versus an extension; Thomas explained that a core field lets everyone use it without an extension and enables a recipient to verify that the key retrieved from the URL matches the one used to sign.
- Stefan Hagen suggested using a fingerprint, but Thomas Schmidt explained a URL (not a fingerprint) is intentional because CSAF uses purely technical, detached signatures that can be updated over time without changing the document itself. Stefan Hagen confirmed his understanding and appreciated the clarification.
- Christoph Plutte pointed out that the linked PGP key in the example was for the contact email, not the key used to sign the whole CSAF document. Thomas Schmidt agreed both use cases are valid. The discussion converged on turning the `contact_details` field into an object with dedicated fields for **email** and for **key material** (kept generic rather than OpenPGP-specific, using MIME types to distinguish OpenPGP keys from S/MIME certificates), while retaining the free-text `contact_details` as a catch-all. The documentation would encourage using the specific fields and only using the free-text field when the specific fields do not apply.
- A motion was presented by Thomas Schmidt to create dedicated fields for email and OpenPGP key, ensure they work with the current contact details field, and provide mappings from CSAF 2.0 to CSAF 2.1. Justin Murphy confirmed the intention to create an issue that would result in a pull request, and Thomas Schmidt agreed to document the motion on the newly created issue (subsequently tracked as Issue [#1511](https://github.com/oasis-tcs/csaf/issues/1511) for the contact PGP key URL). No objections, discussions or concerns were raised. The motion carries. Vijay Sarvepalli removed the `x_extensions` from the example in PR #1487 so that basic examples remain minimal and work without unofficial extensions.
