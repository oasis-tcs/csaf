#### Issue [#1479](https://github.com/oasis-tcs/csaf/issues/1479) - CPEs and product version ranges

Thomas Schmidt introduced the issue: when a CPE version is set to `*` while version ranges are expressed elsewhere, consumers can see conflicting matching outcomes depending on whether they evaluate CPE-only logic or version-range-aware logic.

Options discussed included:

- Do nothing.
- Explicitly allow the current practice and define matching behavior for this conflict.
- Introduce additional range fields similar to CVE JSON 5 (full or reduced variant).
- Move CPE usage to other structural locations (branch relationship/helper variants).
- A possible URI-based alternative (not favored).

Discussion highlights:

- Multiple participants favored option 2 as the smallest, most pragmatic step.
- Concerns were raised that option 3 increases complexity and may increase risk of inconsistent data.
- Thomas Schmidt confirmed that whichever option is chosen, CPE will not become mandatory.
- Justin Murphy handed facilitation over mid-discussion due to a hard stop; Stefan Hagen continued facilitation.

A motion was set by Sonny van Lingen to accept proposal version 2 for issue #1479, seconded by Christoph Plutte (with additional support voiced). No concerns were raised.

- The motion carries.

#### Issue [#1231](https://github.com/oasis-tcs/csaf/issues/1231) - OpenAPI-based CSAF validator API and SARIF output model

- Christian Banse introduced issue #1231, proposing an OpenAPI definition for a CSAF validation service API.
- The proposal includes:
  - A validation endpoint for CSAF 2.0/2.1 documents.
  - Support for test presets and explicit test selections.
  - Discovery endpoints to list available test presets and tests.
  - A findings model aligned with SARIF to maximize interoperability and re-use of established tooling patterns.
- Stefan Hagen noted that SARIF is evolving and suitable as an ecosystem for broader system-analysis findings, not only source-code analysis.
- Thomas Schmidt suggested using the current draft as a starting point for a future Committee Note, with additional implementation feedback and editorial polishing.
- No formal motion was set for acceptance at this meeting; the TC agreed to continue content development first and then proceed with formal OASIS Committee Note mechanics.

#### Issue [#1446](https://github.com/oasis-tcs/csaf/issues/1446) - Require uniqueness for remaining product identification helper arrays

- Thomas Schmidt presented issue #1446, describing an oversight where some product identification helper arrays still allow duplicate entries with identical content.
- Clarification in discussion: "unique" means duplicate entries with no information gain should not be allowed.
- A motion was presented by Thomas Schmidt to make the remaining product identification helper arrays unique, and was seconded by Stefan Hagen.
- No objections were raised. The motion carries.

#### Issue [#675](https://github.com/oasis-tcs/csaf/issues/675) - Clarify `known_not_affected` vs `fixed`

- Thomas Schmidt reintroduced issue #675 to clarify usage guidance:
  - `known_not_affected`: product was not affected.
  - `fixed`: product may have been affected previously but is now fixed.
- Sonny van Lingen asked whether this is purely a prose clarification; Thomas Schmidt confirmed it is a text clarification in the specification.
- Christoph Plutte raised practical interoperability concerns with downstream consumers that only accept subsets of VEX justifications; Thomas Schmidt noted this can be handled using remediation signaling.
- Stefan Hagen raised additional semantic concerns about the "in any version before" wording and compatibility with broader VEX interpretation.
- Due to time, the TC agreed to continue the discussion in the issue; no motion was carried on issue #675 in this meeting.
